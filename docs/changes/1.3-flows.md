# 1.3 changes: key flows (lane flows)

Key flows are flows played by keyboard only. They prove a journey such as a checkout can be finished without a mouse, which is what EN 301 549 clause 9.2.1.1 (WCAG 2.1.1 Keyboard) asks for.

## Flow format

### `keyboard:`

A new top-level key in a flow file.

| Value | Meaning |
|---|---|
| `true` | A key flow, held dry: it stops at the first step that would send something to the site. |
| `send` | A key flow that sends for real (see "Send on request" below). |
| `false`, empty or no key | A mouse flow, as before. |

Any other value fails to parse with exactly `keyboard: "yes" isn't one of true, false, send` (the value quoted as written; a list or mapping shows as `"a list or mapping"`). `keyboard: dry` is rejected too.

### `press` step

```yaml
- press: Tab
- press: {key: Enter, on: ".menu-toggle"}
- press: {key: ArrowDown, times: 3}
```

- `key`: Tab, Shift+Tab, Enter, Space, Escape, ArrowUp, ArrowDown, ArrowLeft, ArrowRight, Home, End (case-sensitive).
- `on`: a selector, or `{selector: ..., text: ...}`, optional. In a key flow focus is moved there with Tab first; in a mouse flow the element is focused directly (no mouse event).
- `times`: 1 to 50, default 1.
- The key is always a trusted key event, in key flows and mouse flows.
- Errors:
  - `press: key "Tabb" isn't one of Tab, Shift+Tab, Enter, Space, Escape, ArrowUp, ArrowDown, ArrowLeft, ArrowRight, Home, End (did you mean "Tab"?)`
  - `press needs a key, such as Tab, Enter or Escape`
  - `line N: press: times is 1 to 50, not 0`
  - `press: on needs a selector or text`
- Step text in issue titles: `press Tab`, `press Shift+Tab 3 times`, `press Space on #terms`, `press Enter on "Open menu" 50 times`.
- Enter and Space presses are refused on production URLs (unless the flow sets `production: true`), as click and submit are.
- Enter and Space presses keep what the flow read with `${env:...}` on the site, as click and submit do. When the press would send the page off the site (or from an https site down to plain http), the step fails with `not sending what the flow typed: <host> isn't the site being checked (<site>); pass --allow-host <host> to open it`. Enter follows a link; Enter or Space on a submit button sends its form to the button's formaction or the form's action; Enter in any other input of a form submits that form. This holds in mouse flows and key flows. It also holds for the Enter a key flow presses to operate a click target. When what has focus can't be read, the press fails with `couldn't tell what has focus, so nothing from the environment is sent: <err>`.
- In a mouse flow an Enter or Space press now waits for the page to settle and fails with `it led off the site: ...` when it left the site, as a click does.

### `expect: focus` and `expect: focus_within`

- `focus: <selector>`: the focused element (read through open shadow roots) matches the selector.
- `focus_within: <selector>`: focus is inside a matching element.
- Both take `absent: true`. A selector with ` >>> ` names an element inside a shadow root, as keyboard traces write them; this now works in every step's selector too.
- Step text: `expect focus #place_order`, `expect focus within [role=dialog]`, `expect no focus #x`.
- Failure text: `focus is on <selector>, not <want>`, `focus isn't inside <want>; it is on <selector>`, `focus is still on <want>`, `focus is still inside <want> (on <selector>)`. Nothing focused shows as `body`.

### Changed messages

- An empty expect: `expect needs text, selector, url, status, focus, focus_within or message` (was `expect needs text, selector, url, status or message`).
- An unknown step lists press: `(actions: goto, click, fill, select, check, submit, press, wait, expect, screenshot)`.
- `flows init` writes the example with the steps line `# Steps: goto, click, fill, select, check, submit, press, wait, expect,` / `# screenshot.` and a new commented line `# keyboard: true     # play it by keyboard only and hold what it would send; send sends it`.

## How a key flow plays

- Every step that acts on an element reaches it with Tab, up to `keyboard.max_tabs` presses (default 150), then with Shift+Tab as many again. Reached means focus is on the target or inside it, through shadow roots. No mouse event is ever sent.
- click: Enter, or Space on a checkbox, radio, role=checkbox, role=radio, role=switch or role=button without href.
- submit: reaches the form's submit button (else its first field), then Enter.
- fill: reaches the field, then types with Input.insertText (no key events carry the value).
- select: reaches the select, then ArrowDown (ArrowUp for an option above) until the option with that value or label is selected.
- check: reaches the box and presses Space when its state differs.
- goto, wait, expect and screenshot work as in a mouse flow.
- Key flows run from the keyboard module, one after another, each in its own private session (logged in with `login: true`). The interact module no longer plays them, so no flow runs twice.
- New run file per key flow: `keyflows/<flow slug>.txt`, one line per keyboard step, such as `step 2 fill "#pass": on #pass after 1 key presses`, `step 2 fill "#pass": <typed 15 characters>`, `step 10 click "#place_order": Enter`. Typed values never appear, only `<typed N characters>`.

## Dry by default, send on request

- `keyboard: true` blocks every request but GET and HEAD for the whole flow. The first click, submit or Enter or Space press that makes the site send one passes and ends the flow. The run gets a note:
  - `note: keyboard: <file> stopped at step <n> (would have sent <METHOD> <path>); steps <n+1>-<last> not run`
  - with one step left: `note: keyboard: <file> stopped at step <n> (would have sent POST /order/); step <last> not run`
  - at the last step: `note: keyboard: <file> stopped at step <n> (would have sent POST /order/)`
- Writes during other steps (fill, select, check, Tab presses, page loads such as WooCommerce's update_order_review), beacons and writes to other hosts are blocked without ending the flow.
- Only the key press that operates the step's control can end the flow. A write the page sends while Tab moves toward the target (an autosave on focusout, WooCommerce's update_order_review, cart fragments) is blocked without ending it. A step whose target Tab never reaches is a keyboard/flow failure even when such a write was blocked during it.
- The hold covers the flow's own tab only. Neither a popup or `target=_blank` form that a key press opens nor messages sent over an open WebSocket are held. A site that places orders that way can still get one from a `keyboard: true` flow.
- `keyboard: true` doesn't lift the production refusal. On a URL listed under `production:` its click, submit and Enter or Space steps are refused with interact/flow-production as in any flow, though the hold would block the write. A dry key flow therefore can't prove a production checkout unless the flow sets `production: true`. This keeps one rule for every flow: the hold misses popups, `target=_blank` forms and WebSocket messages (see above), so it isn't trusted on its own against a live shop.
- `keyboard: send` really submits, with these limits:
  - On a URL listed under `production:` the existing refusal applies: issue interact/flow-production, title `Flow "<name>" step <n> refused on production: <step>`, detail `refused on a production URL (set production: true in the flow to allow it)`.
  - On a public address without `--staging` the flow runs dry, unless it sets `production: true` and starts on a URL listed under production. It gets the note `note: keyboard: send runs only on a loopback or private address, or with --staging; <file> ran dry`. The address counts as public when the runner says so, or when the site's host isn't `localhost`, `*.localhost` or a name or IP that resolves only to loopback, private or link-local addresses. A host that can't be resolved counts as public, so a run that didn't classify its target never sends.
  - The off-site refusal, the environment allowlist (`--allow-env`) and the private session apply as to any flow.
- Key flows run only at `--level flows`. Below it the run gets `note: keyboard: <n> key flows need --level flows (they type test data); not run` (one flow: `note: keyboard: 1 key flow needs --level flows (it types test data); not run`).
- A flow file that can't be read is reported by interact (interact/flow-file) when interact plays flows on the run (module `interact` on and `--level flows`). Otherwise the keyboard module notes it, since the file may hold a key flow: `note: keyboard: flow file <file> can't be read (<error>); a key flow in it is not run`, or for the folder itself `note: keyboard: flows folder <dir> can't be read (<error>); key flows not run`. Which flow the file held can't be told, so it isn't listed under `key_flows.skipped`.
- run.json gains `key_flows` (left out when the flows folder has no key flows): `run` counts the key flows that ran, `skipped` lists `{file, reason}`. Reasons: `needs --level flows`, `needs a login: set SOUNDCHECK_USER and SOUNDCHECK_PASSWORD`, `no browser session`, `the run was stopped`, `logging in failed: <err>`, or a session error. Skips other than level, browser and stopped also give the note `keyboard: <file> not run: <reason>`; no browser gives `keyboard: key flows: no browser session available`.

## Checks

### keyboard/flow

- Error, WCAG 2.1.1, EN 301 549 9.2.1.1, impact critical.
- Title `Key flow can't be finished by keyboard`.
- Source `<flow file base name>: <step kind> <target>`, such as `order.yaml: click #place_order`.
- Detail `<flow name>: step <n> <kind> "<target>": not reached after <max_tabs> Tab stops; focus stayed on <selector>`, or `<flow name>: step <n> <kind> "<target>": reached; <Key> did nothing` when the key changed nothing within 1 s (no DOM change, navigation, request or focus move). A select that doesn't move: `reached; ArrowDown didn't select the option`. A checkbox: `reached; Space did nothing`.
- The issue carries the last 6 focus stops (FocusPath) and the fix `Make the control a native button, link or field, or give it tabindex="0" and handle Enter and Space.`
- It goes on the flow's start page, or into the site issues when the run didn't visit that page.
- Other failures of a key flow (a selector not found, an expect that failed, the start page not opening) are reported as interact reports flows: interact/flow, `Flow "<name>" step <n> failed: <step>` or `Flow "<name>" couldn't open <start>`.

### keyboard/error-not-linked

- Warning, WCAG 3.3.1, EN 301 549 9.3.3.1, impact serious.
- Title `Form errors aren't tied to their fields`.
- After a submit step, or a click on a button in a form, in a key flow (dry or send), Soundcheck waits up to 1 s for errors: fields marked aria-invalid="true" or invalid (:invalid) both before and after the step, or new visible messages matching `[role=alert]`, `[aria-live]`, `.error`, `.woocommerce-error`, `.invalid-feedback` or `.wpcf7-not-valid-tip`.
- It passes when focus moved to the first field with an error, or to an element that holds or repeats an error message (an error summary), or when every such field has aria-describedby or aria-errormessage pointing at text. Native browser validation (focus moves to the first invalid field) passes.
- A form a script reset after sending (its required fields invalid again) shows no error. A new message in a live region is announced, so it counts only alongside fields that show errors. A step whose write a dry flow held isn't checked: the page then answers the hold, not the form.
- Source the form's selector. Detail `After <flow name> step <n>, <k> fields show errors but focus stayed on <selector> and the errors aren't linked with aria-describedby or aria-errormessage.` With one field: `1 field shows errors`. When no field is marked, k counts the error messages.
- Fix `Move focus to the first field with an error or to an error summary, or point each field at its message with aria-describedby or aria-errormessage.`
- The key flow's trace gets a line such as `step 4: #contact shows 1 error not tied to its fields; focus on #send`.

## Templates

Four key flow templates, all `keyboard: true`, each starting with a comment that explains it and the difference between `true` and `send`:

- `keyboard-checkout.yaml`: WooCommerce `/checkout/`. Fills the billing fields with `${fake:...}`, ticks `#terms` with Space, expects focus on `#terms`, reaches Place order by Tab like any other control and clicks it (dry: stops there) and expects `Thank you`.
- `keyboard-contact.yaml`: `/contact/`. Fills name, email and message of the form that has a textarea and submits it.
- `keyboard-menu.yaml`: `/`. Tabs to the menu toggle (`.menu-toggle, button[aria-controls][aria-expanded]`), presses Enter, expects `[aria-expanded=true]`, presses Tab and expects focus within `nav`. The toggle often shows at mobile widths only.
- `keyboard-dialog.yaml`: `/`. Tabs to the first `[aria-haspopup=dialog]`, presses Enter, expects focus within `[role=dialog], dialog[open]`, presses Escape, expects focus out of the dialog and back on the trigger.

They are offered by `init --eaa` (lane cli) through `flow.KeyboardTemplates()`.

## Interact fixes

- A field is never named by its value in issue titles and results. Only a button's value (button, input type=button, submit or reset) is its caption. Fields are named by aria-label, aria-labelledby text, title, their label's text (without the fields in it), placeholder or name. An unnamed field falls back to its selector. Before, a prefilled email such as a customer's address could show in `Form field has no name: <value>`; now it reads `Form field has no name: Your email` (placeholder) or `Form field has no name: #bare` (selector). Titles derived from a value change; others stay the same.
- Mouse flows only: interact skips flows with `keyboard:` set. A flows folder with only key flows gets no "has none" note from interact. When the keyboard module is off (no `--eaa`, `+keyboard` or `modules: keyboard`), those key flows run nowhere, so interact adds the note `note: keyboard: <n> key flows need the keyboard module (--eaa or +keyboard); not run` (one flow: `note: keyboard: 1 key flow needs the keyboard module (--eaa or +keyboard); not run`). run.json `key_flows` stays absent in that case.
- Field names in `interact/unnamed-field` titles and candidate labels now follow the accessible name order more closely: a field's aria-labelledby text comes before its title. A label's text is read with textContent (text hidden by CSS inside the label counts) without the fields in it. Titles of unnamed-field issues (so their issue keys too) can change for fields that have both aria-labelledby and title, or labels with hidden text, not only for value-derived ones.
