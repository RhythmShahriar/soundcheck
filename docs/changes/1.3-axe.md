# 1.3 changes: axe baseline, audit-aware compare and run safety (lane axe)

Everything a user can see that the axe lane changed for 1.3: which accessibility rules run, the new fields on issues and pages, how a compare treats audits that didn't finish or rules the baseline never ran, three new checks, the browser's network scope, file modes and the axe-core SBOM. Exact text is in backticks.

## Rule sets and the WCAG version

- New snapshots run the WCAG 2.1 A and AA rules by default (1.2 ran the WCAG 2.0 rules). Choose with `--wcag 2.0|2.1|2.2` (cli lane) or the config block below. A compare uses the version its snapshot recorded in `run.options.wcag`; a 1.2 snapshot has none and counts as 2.0.
- What each version runs: 2.0 runs axe-core's `wcag2a` and `wcag2aa` rules; 2.1 adds `wcag21a` and `wcag21aa` (new: `autocomplete-valid`, `avoid-inline-spacing`, `label-content-name-mismatch`); 2.2 adds `wcag22aa` (new: `target-size`). Experimental rules stay off.
- New config block:

  ```yaml
  a11y:
    wcag: "2.1"        # 2.0, 2.1 or 2.2 (quoted or bare)
    max_elements: 20   # elements kept per rule and page, 1 to 200
    iframes: false     # true also audits same-origin iframes
  ```

  - A bad version, from the file or `--wcag`, fails with exit 2: `--wcag (a11y.wcag): "2" isn't one of 2.0, 2.1, 2.2`.
  - A bad cap: `<file> line N: a11y.max_elements: must be a number from 1 to 200`.
  - A typo: `unknown setting "a11y.max_element" (did you mean "a11y.max_elements"?)`.
  - With `iframes: true`, issues in a frame have selectors such as `#frame-id >>> input[name="email"]`. Cross-origin frames are never audited.
- run.json records the rule set once per run under `options.a11y`: `axe` (`4.14.0`), `axe_sha256`, `tags`, `rules` (sorted rule ids, including the module's own `overlay`, `placeholder-label` and, for 2.1 and 2.2, `reflow`) and `max_elements`. It is absent when no page was audited.
- `--list-checks` now describes `a11y/<axe rule id>` as: `The A and AA rules of the WCAG version the run uses (2.1 unless a11y.wcag or --wcag says 2.0 or 2.2), each issue naming the WCAG criteria and EN 301 549 clauses it fails. The rule ids are axe-core's (https://dequeuniversity.com/rules/axe/); ignore: rules in the config name them as a11y/<rule id>.`

## New fields on issues and changes

- Every a11y issue carries `wcag` (criteria such as `1.4.3`, sorted by number so 1.4.3 comes before 1.4.12), `en301549` (clauses such as `9.1.4.3`) and `impact` (the element's impact, else the rule's). Under 2.0 and 2.1 the criteria only WCAG 2.2 has (2.4.11, 2.4.12, 2.4.13, 2.5.7, 2.5.8, 3.2.6, 3.3.7, 3.3.8, 3.3.9) and their clauses are left out.
- Changes in a compare (NEW, BROKE, FIXED and ignored) copy `wcag`, `en301549`, `impact` and `focus_path` from their issue.
- Rules about the document itself, such as `html-has-lang`, `html-lang-valid` and `document-title`, were dropped before 1.3. They now report with source `html` (or `body`).

## The `audits` field on pages

- Each page in run.json gets `audits.a11y` when the a11y module ran on it:
  - `{status: ok}` when axe-core finished;
  - `{status: timeout, reason: "axe-core timed out after 45s"}`;
  - `{status: error, reason: ...}` with the error, secrets masked, at most 200 characters (a result over 2 MB is the error `axe-core result too large`);
  - `{status: skipped, reason: "status 500"}` for a page with status 400 or above.
- `frames` lists the hosts of iframes that were not audited (cross-origin always; same-origin too unless `iframes: true`). `capped_rules` maps a rule id to its total element count when it found more than `max_elements`; the status stays `ok`.
- Firefox and WebKit runs record `{status: skipped, reason: "needs Chrome"}` for every Chrome-only module left out (a11y, interact, speed and others).
- The warning for a failed audit now reads `a11y: <path>: axe-core: <reason>; the page's a11y results are missing; the statement marks it`, for example `a11y: /shop/: axe-core: timed out after 45s; the page's a11y results are missing; the statement marks it`.

## Compare: not checked instead of FIXED

- When a page's audit of a11y, keyboard or any module with audits didn't finish in either run, that module's changes on the page are not counted. They move to `ignored` with the reason `not checked on this page: <module> timed out` (or `failed`, `skipped`). The comparison warns once per page and module: `not checked: <path> (<module>: <reason>); its issues are kept from the snapshot, not counted as fixed`. The reason is `not audited` when the later run lists the module but the page has no audit.
- A page in a 1.2 snapshot without `audits` counts as audited, so upgrading doesn't hide anything.
- A keyboard walk capped on the later run (`keyboard.max_tabs`) counts as finished. Still, a keyboard issue it no longer reports isn't FIXED: the walk stopped before it could tell. The issue moves to `ignored` with the reason `not checked on this page: keyboard capped` and the same warning, for example `not checked: /form/ (keyboard: <the audit's reason>); its issues are kept from the snapshot, not counted as fixed`. Issues the capped walk still reports, or that a clean walk no longer finds, are diffed as usual.
- In `--confirm`, a re-visit whose audit didn't finish moves the NEW or BROKE change to UNSTABLE. So does a capped keyboard re-walk that doesn't find the issue again.

## Compare: rule-set and cap guards

- Rule-set guard: a NEW or BROKE `a11y/<rule>` change for a rule the snapshot didn't run goes to `ignored` with the reason `rule not in the baseline`. A 1.2 snapshot counts as the WCAG 2.0 rules of axe-core 4.14.0. One warning names the rules involved: `note: 3 rules didn't run in the baseline (autocomplete-valid, avoid-inline-spacing, label-content-name-mismatch); their issues aren't counted as new. Take a new snapshot to include them` (`note: 1 rule didn't run ...` for one). It shows whenever the rule sets differ and a11y ran in both runs. A 1.2 snapshot compared with a 2.1 run lists six rules: the three above plus `overlay`, `placeholder-label` and `reflow`.
- The other way round: a FIXED change for a rule the later run didn't apply (a 2.2 snapshot compared with a 2.1 run: `target-size`) goes to `ignored` with the reason `rule not in this run`.
- Cap guard: a NEW change for a rule the snapshot capped on that page goes to `ignored` with the reason `beyond the elements kept per rule`. A FIXED change for a rule the later run capped counts only as far as the rule's total really dropped; otherwise those FIXED changes are ignored with the same reason. So fixing one of 300 contrast problems still shows as one FIXED.
- Against a 1.2 snapshot, a NEW or BROKE a11y change on `html` or `body` goes to `ignored` with the reason `the baseline didn't report the page's <html> or <body>`, so a missing `lang` on every page doesn't turn NEW on upgrade.
- Order on a page: unfinished audit first, then rule set, then cap.

## Ignore rules

- An ignore rule can match by `source:` (a glob on the change's source, like `check`, `title` and `pages`). A rule with only `source:` is valid. Only `*` is special, so a selector copied from a report, such as `input[name="email"]`, matches itself with its brackets as they are.
- The warning for an empty rule now reads `ignore rule <n> has no check, title, source or pages and would hide every change; it is skipped`. Expiry and other warnings name the source when set, for example `ignore rule 2 (check a11y/*, source "footer *") expired on ...`.

## Three new checks

| Check | Level | Title | WCAG | EN 301 549 |
|---|---|---|---|---|
| `a11y/placeholder-label` | warning | `Form field is labelled only by its placeholder` | 3.3.2 | 9.3.3.2 |
| `a11y/reflow` | warning (WCAG 2.1 and 2.2 only) | `Page scrolls sideways at 320 px wide` | 1.4.10 | 9.1.4.10 |
| `a11y/overlay` | notice | `Accessibility overlay widget found` | none | none |

- `a11y/placeholder-label`: a visible input, textarea or select whose only name is its placeholder. Detail: `The only name is the placeholder "<placeholder>", which disappears when someone types.` Fix: `Add a visible <label for> or aria-labelledby that points at visible text.` Impact serious. Search fields, the only text field of a form with a visible text button and fields already reported as `a11y/label` are left out. Over `max_elements`, each detail adds `The first <n> of <total> fields named only by their placeholder on the page are reported.` A failure of this check alone warns `a11y: <path>: placeholder check: <error>`.
- `a11y/reflow`: the page is checked at 320 by 640 CSS px. Detail: `At 320 CSS px the page is <n> px wide; <selectors> stick out.` (`sticks out` for one). Fix: `Let the content wrap at 320 px: relative widths and max-width: 100% instead of fixed widths; wide tables or code in their own scrolling box.` Impact serious. Tables, code, media, maps and other content that may scroll in two directions are left out. A failure warns `a11y: <path>: reflow check at 320 px: <error>`.
- `a11y/overlay`: the page loads an overlay widget (accessiBe, UserWay, EqualWeb, AudioEye, Enable, Access Ally or the WordPress plugin pojo-accessibility). Detail: `This page loads <what>. Overlay widgets don't make a site accessible; the FTC's 2025 order against accessiBe is about claims like that: https://www.ftc.gov/news-events/news/press-releases/2025/04/ftc-approves-final-order-requiring-accessibe-pay-1-million`. Fix: `Fix the problems the other checks report in the site itself; don't rely on the widget or claim it makes the site accessible.` Impact minor. One per page, also when axe-core failed.
- `--list-checks` lines:
  - `a11y/placeholder-label  warning  Form field is labelled only by its placeholder (WCAG 3.3.2)`
  - `a11y/reflow  warning  Page scrolls sideways at 320 px wide (WCAG 1.4.10)`
  - `a11y/overlay  advisory  Accessibility overlay widget found (no WCAG criterion)`

## Network scope

- Chrome tabs the run opens block requests to link-local addresses (169.254.0.0/16, fe80::/10) and the cloud metadata names `metadata.google.internal` and `metadata` for every target. When the target is a public address, they also block loopback (127.0.0.0/8, ::1, `localhost`, `*.localhost`, 0.0.0.0), private (RFC 1918, fc00::/7) and 100.64.0.0/10 addresses. The site itself (same host and port, with or without www) and `--allow-host` hosts are always allowed. A target that doesn't resolve counts as public.
- A blocked request shows in `pages[].failed` with the error `blocked by Soundcheck's network scope`.
- A response that arrives from an address out of scope (DNS rebinding) is left out of `pages[].resources`, listed in `failed` with the same error and warned once per host and address: `blocked a response from <host> at <ip>: private address while the target is public`.
- The run's own requests (the target, robots.txt, sitemaps and module requests) refuse addresses outside the target's network: `refusing to connect to <ip>: private address outside the target's network`. A proxy is used as configured.
- Firefox and WebKit can't intercept requests, so their tabs have no scope; the run's own requests are guarded on every engine.
- Known limits: Chrome doesn't pause WebSocket handshakes for interception (nor block them by URL), so a page's `new WebSocket("ws://127.0.0.1:...")` isn't stopped by the scope. Tabs that the cache, interact and login modules open themselves aren't scoped yet. A response from a name that resolved to an address out of scope is dropped from the record after the page got it, so a screenshot can still show it.

## File modes

- `.soundcheck/`, `runs/`, `snapshots/`, `.incoming/` and each run and snapshot folder are created private to the user (0700, was 0750). Files the run writes (run.json, pages.jsonl, the journal, lock files, screenshots, traces and the EAA files) are 0600 whatever the umask. Existing folders and files keep their modes and keep working.
- Writing inside a run folder refuses symlinks from the run folder down: `refusing to write through a symlink: <path>`.

## axe-core SBOM and updates

- Each release archive gets an SPDX SBOM (`<archive>.sbom.json`). The release also ships `axe-core.cdx.json`, a CycloneDX 1.6 SBOM of the bundled axe-core (`pkg:npm/axe-core@4.14.0`, MPL-2.0, with the SHA-256 of `axe.min.js`). Both are listed in `checksums.txt`.
- For contributors: `scripts/update-axe.sh <version>` updates the bundled axe-core after checking the npm integrity and registry signatures and refreshes the SBOM. It refuses to run for Dependabot.
