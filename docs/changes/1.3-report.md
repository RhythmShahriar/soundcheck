# 1.3 changes: reports, history and fleet

What `--eaa` changes in the terminal view, the JSON, Markdown, HTML and JUnit reports, the client report, `history` and `fleet`. Results without `--eaa` look as they did in 1.2, except for the accept hints (first section) and the HTML report's colors and CSP (HTML section).

## Terminal

Under every issue and change that maps to WCAG criteria, after `source:`:

```
  wcag: 1.3.1, 4.1.2 · EN 301 549 9.1.3.1, 9.4.1.2
```

The EN 301 549 part is left out when the issue has no clauses.

Under a `keyboard/*` issue with a focus path, the last six focus stops, a stop repeated in a row folded into one:

```
  path: #billing_email → #billing_phone → #card-element > div:nth-of-type(1) ×4
```

`--plain` writes words instead of glyphs, as ` > ` and a trailing ` x4` would read as part of a CSS selector: `path: #billing_email then #billing_phone then #card-element > div:nth-of-type(1) (4 times)`. In the live view the path wraps inside the card, so its end (where the problem is) always shows.

Accept hints: `  rhythm soundcheck accept <id> if this is expected` is now printed on BROKE and NEW lines as well as CHANGED, in every comparison with a named snapshot (with or without `--eaa`). FIXED, SLOWER and UNSTABLE get none.

An `a11y/*` or `keyboard/*` problem on more than 3 pages ends its page list with the total: `/, /shop/, /about/ +35 more (38 pages)`.

A run or snapshot made with `--eaa` prints, before its summary, one line per page a module couldn't audit:

```
not checked: /catalog/ (a11y: axe-core timed out after 45s); its issues are kept from the snapshot, not counted as fixed
```

A comparison doesn't repeat these lines: its warnings already say the same.

Before the verdict, the counts line:

```
Accessibility: 5 of 50 WCAG 2.1 A and AA criteria have failures · 21 had none found by these tests · 24 need a person
```

A comparison adds the criteria whose failures are all new and the open issues before and after:

```
Accessibility: 4 of 50 WCAG 2.1 A and AA criteria have failures (2.1.2 new) · 22 had none found by these tests · 24 need a person · open issues 3 → 4
```

`--plain` writes `open issues 3 to 4`. Findings of UNSTABLE changes (seen once, gone when the page was checked again) aren't counted: not as open, not against their criteria and not in history.jsonl or the statement. Pages whose audit didn't finish (`note: not checked: ...`) are listed before this line, which they qualify.

The total is 50 criteria for WCAG 2.1 and 55 for 2.2.

Verdict: an `--eaa` result with no issues says `no failures found by these tests` instead of `all clear`, for example `Snapshot "eaa-1" saved; no failures found by these tests - 0 errors, 0 warnings, 0 notices - 6 pages · 31s`. The live panel shows the same words in place of `✓ no problems found`. The words are used only when no criterion has failures: findings set aside by ignore rules (or kept from the snapshot for a page whose audit didn't finish) still fail their criteria. The verdict then counts those criteria instead, as in `Nothing changed; 1 WCAG criterion has failures` or `Snapshot "good" saved; 2 WCAG criteria have failures`. An `--eaa` result with notices and no errors or warnings never says `all clear` either. An axe notice that fails 1.4.4 gives `1 WCAG criterion has failures - 0 errors, 0 warnings, 1 notice`; notices of other modules alone (a missing favicon) give `no failures found by these tests`. The Markdown and HTML report heads say the same. The snapshot panel adds that line under the counts.

Evidence note: every `--eaa` result ends with this sentence, wrapped at the terminal width, also under `-q` (where it is the only extra line):

> Automated and keyboard tests find some accessibility problems, not all. This is evidence for your own review, not a statement that the site meets WCAG, EN 301 549 or the European Accessibility Act.

`-v`: each page the keyboard module walked gets a line such as `keyboard: / 23 stops, 3 widgets (menu, dialog, details), 0.9s`.

## JSON (`--json`)

- Run, snapshot and comparison JSON carry a top-level `eaa` object when the result was made with `--eaa`: `wcag`, `en301549`, `axe`, `criteria` (`failed` with `id`, `issues` and `pages`; `no_failures_found`; `not_tested`), `keyboard` (`pages_walked`, `widgets_tested`, `flows_run`, `flows_skipped`), `not_audited`, `open`, `interrupted` and `evidence_note` (always the sentence above). The criteria lists are `[]`, never `null`.
- Issues and changes gain `wcag`, `en301549`, `impact` and `focus_path` where they apply.
- No `eaa` without `--eaa`. Runs stored by 1.2 load and render in every format.

## Markdown (`--md`, the PR comment)

- Rows of `a11y/*` and `keyboard/*` checks get their criteria after the title: `Keyboard focus is trapped: Card number (2.1.2)`.
- A new section before the notes:

```
### Accessibility (WCAG 2.1 A and AA)

4 of 50 criteria have failures · 22 had none found by these tests · 24 need a person · 4 open issues

<details><summary>Criteria with failures</summary>

| Criterion | EN 301 549 | Issues | Pages |
|---|---|---:|---:|
| 2.1.2 No Keyboard Trap | 9.2.1.2 | 1 (new) | 1 |

</details>

Not checked, so their issues are kept from the snapshot and not counted as fixed:

- `/catalog/` (a11y: timeout)

> Automated and keyboard tests find some accessibility problems, not all. ...
```

The section holds counts, check ids, criteria and paths only: never an issue's title, detail, source or a screenshot, since a PR comment is read by everyone with access to the repository.

## HTML report

- Every report (with `--eaa` or not) now has `<meta http-equiv="Content-Security-Policy" content="default-src 'none'; img-src data:; style-src 'unsafe-inline'; script-src 'sha256-<hash>'">`. Opened from disk it makes no network requests.
- Light theme colors are darker so all text and badges reach 4.5:1 contrast; dark theme badges have dark text.
- An `--eaa` report has two tabs, `Results` and `Accessibility`. The Accessibility tab has the counts line and the evidence note, the pages not checked, a grid of the WCAG criteria in four columns (Perceivable, Operable, Understandable, Robust) with each tile's state as a word and an icon (`✕ failures (<n>)`, `○ none found`, `? needs a person`), the issues by criterion then page, a keyboard walk per page (summary, focus path as a numbered list of up to 150 stops with `(page)` for the page itself, `focus path not available` without a trace, element pictures) and a box with `rhythm soundcheck statement -o accessibility-statement.md`.
- `report --serve` sends its own CSP header that allows the review buttons.

## JUnit (`--junit`)

An `--eaa` result gets, besides the usual suites, one suite per page (`soundcheck.page /checkout/`) with one test case per page and module: `/checkout/ · a11y` and `/checkout/ · keyboard` (classname `soundcheck.a11y`, `soundcheck.keyboard`).

- A case has one `<failure>` per error-level issue of that module on that page, so a keyboard trap fails `/checkout/ · keyboard`. The failure's text lists the check, `wcag:` and `path:` lines, source, detail and fix.
- For a single run, `--fail-on` as a level still applies: errors fail at the default and at every level.
- For a comparison, only errors that a failing change covers (BROKE or NEW at the default `--fail-on`) fail the case. An error the snapshot already had is written as the case's output (`error: <title>` and its lines), so a compare that passes doesn't show a failed test.
- A module that didn't finish on a page (timeout, error, skipped) makes that case skipped, with `not checked: a11y: <reason>` as its output. A page that couldn't be visited skips both cases.
- A partial (interrupted) result fails no case; the issues are output.
- Results without `--eaa` have the same JUnit as in 1.2.

## Client report (`report --client`)

When the result was made with `--eaa`:

- "What we checked" says `Accessibility evidence: WCAG <version> AA automated rules and a keyboard walkthrough of <n> pages` instead of `Accessibility basics`, for example `Accessibility evidence: WCAG 2.1 AA automated rules and a keyboard walkthrough of 3 pages`.
- A new `Accessibility` section: `We tested the site against the WCAG 2.1 A and AA criteria with automated rules and by using it with the keyboard alone.`, four counts (`Open accessibility problems` (problems set aside by ignore rules are not open, though the criteria list still counts them), `Criteria with failures`, `Criteria with none found by these tests`, `Criteria a person needs to check`), the list `Criteria with failures` (`2.1.2 No Keyboard Trap (1 problem on 1 page)`), the pages the tests couldn't finish (`We couldn't finish the accessibility tests on /catalog/, so that page needs checking again.`), a collapsed `What still needs a person (<n> criteria)` list with `These tests can't judge these criteria; someone needs to check them by hand.` and the evidence note.
- Criteria names come from the WCAG catalog; the section never shows selectors, check ids or a reason text from the site.

Without `--eaa` the client report is unchanged (it still says `Accessibility basics` when the a11y module ran).

## History (`history`, `history.jsonl`)

- Each line of a run with the a11y or keyboard module on (every `--eaa` run) gains `a11y_open` (distinct `a11y/*` problems), `keyboard_open` (distinct `keyboard/*` problems) and `a11y_by_criterion` (both, by WCAG criterion). A run without the module leaves its count out, so a missing count means "not measured", never 0: a clean `--eaa` run writes `"a11y_open":0,"keyboard_open":0`.
- `history --metric a11y` shows the column `A11y open`, `--metric keyboard` shows `Keyboard open`. An entry without the count shows `-`. The footer:

```
A11y open  31 to 4 (-87%)  █▅ ▆▁
Worst criteria now: 1.4.3 Contrast (3), 1.3.1 Info and Relationships (1), 2.1.2 No Keyboard Trap (1)
```

  `--plain` leaves out the sparkline. The worst criteria are the top 3 of the latest entry that has counts, titles shortened ("Contrast (Minimum)" is "Contrast"). With no counts at all: `A11y open  not measured: no run had the a11y module on (--eaa turns it on)`.
- `--page <path>` with a11y or keyboard shows that page's open problems (column `A11y open <path>` or `Keyboard open <path>`, no `Worst criteria now:` line). The history keeps the counts of the first 50 pages of each run (`page_metrics[].a11y_open` and `keyboard_open`). A page it doesn't have: `no a11y counts for <path> in the history; it keeps the first 50 pages of each run with the a11y module on` (exit 2).
- `page_metrics[].path` masks a token in the path the way the statement draft does (`/reset/•••••/`). `--page` takes the path as the visitor sees it and finds the masked one.
- History files written by 1.2 load and render with every metric.

## Fleet (`fleet`)

- A site in `sites.yaml` takes `eaa: true`. Its command then gets `--eaa` after the site's own args, unless those args or the fleet's own flags (`fleet ... --eaa`) already have it, so it is never doubled. A misspelled key such as `eea:` is refused as before.
- `fleet.html` gains the columns `Open accessibility issues` (accessibility and keyboard issues together) and `Criteria with failures` when any site ran with `--eaa`. A site without `--eaa` has empty cells there, not 0. The open issues cell shows the trend against the site's previous fleet run as an arrow with words (`↑ up from 9 at the last fleet run`, `↓ down from 9 at the last fleet run`, `→ same as at the last fleet run`) and links the site's `Statement draft`.
- `fleet.json` gains, per site, `eaa_open` (the open accessibility and keyboard issues together, the run's `eaa.open`; history.jsonl splits them into `a11y_open` and `keyboard_open`), `criteria_failed`, `eaa_trend` (`up`, `down` or `same`; absent without a previous fleet run with eaa data for that site), `eaa_before` (the previous count) and `statement` (the draft's path relative to the fleet folder). All are absent for a site without `--eaa`.
- Each `--eaa` site's run writes its own `eaa/statement-draft.md` in its run or snapshot folder inside the site's fleet folder.
