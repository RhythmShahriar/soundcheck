# 1.3: the keyboard module

Notes for the docs team from the keyboard lane. Everything here is what a user can see: the module, its checks, its config, what the walk does and never does, its limits and the files it writes. Exact text is in backticks.

## The module

- New module `keyboard`. It walks every page with real key presses in Chrome (trusted CDP key events, never script events), after interact's clicks and submits. It needs Chrome: with the plain HTTP fetcher every page gets the audit `skipped` with reason `needs Chrome`.
- `--eaa` adds it to the module list next to `a11y` (wired by the CLI). It can also be named in `--modules` or `modules:`.
- `--list-checks` lists its 15 checks with level, title and a short fix (below).
- A page interact clicked or submitted on is loaded once more before the walk, so the walk starts from a clean page.
- Under `-v` the report prints one line per page: `keyboard: <path> <stops> stops, <widgets> widgets (<kinds>), <seconds>s` (printed by the report).

## Checks

Every keyboard issue is keyed by check and selector, never by an accessible name, so a label that changes (a signed-in customer's email in a link) doesn't make an issue new. The criteria follow the run's WCAG version (`2.1` by default, `2.2` with `--wcag 2.2`); the EN 301 549 clause is `9.` plus each criterion. At most 20 issues per check per page.

| Check | Level | Impact | WCAG / EN 301 549 | Title |
|---|---|---|---|---|
| `keyboard/trap` | error | critical | 2.1.2 / 9.2.1.2 | `Keyboard focus is trapped` |
| `keyboard/not-reachable` | warning | serious | 2.1.1 / 9.2.1.1 | `Clickable element can't be reached by keyboard` |
| `keyboard/not-operable` | warning | serious | 2.1.1 / 9.2.1.1 | `Control doesn't respond to Enter or Space` |
| `keyboard/menu` | warning | serious | 2.1.1 / 9.2.1.1 | `Submenu doesn't open by keyboard` |
| `keyboard/focus-lost` | warning | serious | 2.4.3 / 9.2.4.3 | `Focus is lost after closing` |
| `keyboard/dialog-focus` | warning | serious | 2.4.3 / 9.2.4.3 | `Dialog doesn't take or keep focus` |
| `keyboard/no-focus-ring` | warning | serious | 2.4.7 / 9.2.4.7 | `No visible focus indicator` |
| `keyboard/focus-invisible` | warning | serious | 2.4.7 / 9.2.4.7 | `Focused element is hidden` |
| `keyboard/context-change` | warning | serious | 3.2.1 / 9.3.2.1 | `Moving focus changes the page` |
| `keyboard/skip-link-broken` | warning | moderate | 2.4.1 / 9.2.4.1 | `Skip link doesn't move focus to the content` |
| `keyboard/skip-link-missing` | notice | minor | none (advisory) | `No skip link before a long run of stops` |
| `keyboard/escape` | notice | minor | none (advisory) | `Escape doesn't close it` |
| `keyboard/focus-obscured` | notice | moderate | 2.4.11 / 9.2.4.11 with WCAG 2.2, else none | `Focused element is covered by fixed content` |
| `keyboard/flow` | error | critical | 2.1.1 / 9.2.1.1 | `Key flow can't be finished by keyboard` |
| `keyboard/error-not-linked` | warning | serious | 3.3.1 / 9.3.3.1 | `Form errors aren't tied to their fields` |

`keyboard/flow` and `keyboard/error-not-linked` come from flows marked `keyboard: true` (the key flows lane documents them). The others come from the page walk. Details, with `<name>` the element's accessible name (masked, see below; the tag alone when there is none):

- `keyboard/trap`: `Tab and Shift+Tab kept focus here for <n> presses; <k> focusable elements after it (<selector>, <selector> ...) can't be reached.` Source: the trapping element, or the first element of a 2 or 3 element cycle. The issue carries the last 6 stops as its focus path. Not a trap: a cycle that passes the page itself, a modal dialog that Escape closes, a cross-origin frame held for fewer than 50 presses each way, nothing focusable after it, Escape then Tab getting out, or a walk that was capped or timed out.
- `keyboard/focus-invisible`: `Tab stop <n> (<tag> "<name>") has focus but is hidden (<opacity 0|visibility hidden|clipped to 1 px|outside the viewport>).`
- `keyboard/focus-obscured`: `Tab stop <n> (<tag> "<name>") is fully covered by <selector>.`
- `keyboard/context-change`: `Moving focus to <tag> "<name>" with Tab <opened a new page|opened a new window|sent a form> without Enter.` A navigation in the first 2 s after load is not counted.
- `keyboard/skip-link-broken`: `Skip link "<name>" points at #<id>, which <doesn't exist|isn't where the next Tab goes>.`
- `keyboard/skip-link-missing` (Source `document`): `<n> Tab stops come before the main content and none of the first 3 is a skip link.` Only with at least 10 stops before the main landmark, or no main landmark at all. With `skip_link: required` it is a warning failing 2.4.1 / 9.2.4.1 from 1 stop; with `skip_link: off` it never fires.
- `keyboard/no-focus-ring`: `Tab focus on "<name>" changes <n> pixels around it; people using a keyboard can't see where they are.` Measured by comparing screenshots of the area around the element with and without focus (fewer than 20 changed pixels fails), on up to 40 stops per page, desktop only. A stop whose unfocused look keeps changing (an animation) is not judged. Neither is one that loses focus before its focused screenshot is taken (a page script moves focus) twice in a row; the first time it is pictured again. Results are reused for the same selector on other pages of the same URL group.
- `keyboard/focus-lost`: `After <Escape|Enter on the close control|toggle> on "<name>" focus went to <the page body|a removed element|a hidden element>.`
- `keyboard/dialog-focus`: `The dialog opened by "<name>" didn't get focus.` or `The dialog opened by "<name>" let Tab reach <selector> behind it.` (modal dialogs only).
- `keyboard/escape`: `The <dialog|menu> opened by "<name>" is still visible 500 ms after Escape.`
- `keyboard/menu`: `The submenu of "<name>" doesn't open with <Enter, Space or ArrowDown|Tab>.`
- `keyboard/not-reachable`: `<tag> "<name>" reacts to <event> but Tab never reaches it.` The element has its own `click`, `mousedown`, `pointerdown`, `mouseup` or `pointerup` listener. Listeners on the document, the body or a container with more than 5 child elements (delegation), elements inside a focusable element or a label, boxes under 4x4 px and inert, hidden or `pointer-events: none` elements are left out.
- `keyboard/not-operable`: `<tag> "<name>" reacts to a mouse click but not to Enter or Space.` Reported when Enter and Space did nothing for 500 ms each and one mouse click at its centre did.

## Config

New block `keyboard:` in `.soundcheck/config.yaml`:

```yaml
keyboard:
  max_tabs: 150        # 10 to 2000: Tab presses per page before the walk stops
  widgets: 10          # 0 to 200: menus, dialogs, disclosures and custom controls tested per page
  trap_after: 4        # 3 to 20: presses on the same element before it counts as a trap
  skip_link: expected  # expected, required or off
  pages: ["/cart*", "/checkout*", "/my-account*", "/contact*"]  # widgets are tested here as well
  ignore: []           # CSS selectors the walk records but never judges or presses
```

Widgets are tested on the first walked page of each URL group and on every page matching `pages`. Errors (the CLI adds the file name):

- `keyboard.max_tabs: must be a whole number from 10 to 2000, not 9`
- `keyboard.widgets: must be a whole number from 0 to 200, not 201`
- `keyboard.trap_after: must be a whole number from 3 to 20, not 2`
- `keyboard.skip_link: must be expected, required or off`
- `keyboard.pages: "shop/*" isn't a path: write it from the site's root, such as /checkout*`
- `keyboard.ignore: "<value>" isn't a CSS selector: give one selector of at most 300 characters on one line`
- `unknown setting "keyboard.max_tab" (did you mean "keyboard.max_tabs"?)`

## What the walk does and never does

The walk presses Tab and Shift+Tab over the page, Escape and Tab once to test a suspected trap, Enter on a skip link (a link to `#id` on the same page), Enter, Space, ArrowDown, Escape and Tab on widget triggers and Enter and Space on focusable custom controls, plus one mouse click on a custom control no key worked on.

While it has the page it never:

- sends anything: requests other than GET and HEAD, WebSocket connections and connection upgrades are stopped before they leave the browser, also those of the page's service worker;
- leaves the page: navigations that aren't to a fragment of the same page are stopped, windows the page opens are closed;
- presses a link to another page, a form's submit control or anything that looks destructive (delete, remove, log out, sign out, unsubscribe, cancel order, place order, pay, buy, checkout, empty cart and the same words in German, French, Spanish, Italian and Dutch);
- downloads files, opens a file chooser, accepts an alert, confirm or prompt, grants a permission (location, notifications, camera, microphone, clipboard, MIDI) or answers a passkey request;
- walks `/wp-admin` or `/wp-login.php` pages (audit `skipped`, reason `admin pages are never walked`);
- acts inside a frame from another origin: for such a frame it records only the host and how many stops it holds;
- reads the value of a field: names come from Chrome's accessibility tree.

Everything it held or stopped is listed in the trace (`held` and `events`), such as `POST /cart`, `navigation stopped: GET /away`, `download blocked: GET /file.pdf`, `WebSocket refused: <host>`, `file chooser canceled`, `dialog dismissed: alert`, `window opened and closed: <host>`, `passkey request refused: get`. A guard Chrome refused to set is listed as an event too, such as `downloads not denied: <error>`; the walk goes on, since requests that write are held either way. Paths in them have no query string and token-like segments masked (`POST /password/reset/***`). Refusals a page fakes by firing the events itself are not recorded.

## Masking

Every accessible name and every Detail the module writes is masked: credentials (the same rules as everywhere in Rhythm), email addresses (`***@***`), phone numbers (international such as `+49 30 1234567` and local with separators such as `(030) 123-4567`), card numbers (13 to 19 digits passing the Luhn check, grouped or not) and IBANs with a valid checksum become `***`. A 16-digit order number that isn't a card number, a plain run of digits and dates stay as they are.

## Limits and their warnings

Each page has an audit `keyboard` in run.json: `ok`, `capped`, `timeout`, `error` or `skipped`, with a reason:

- `skipped`: `needs Chrome`, `the page didn't load`, `HTTP <status>` or `admin pages are never walked`.
- `capped`: `stopped after <max_tabs> Tab stops (keyboard.max_tabs)` or `Tab stop <n> (<tag>) left the page`.
- `timeout`: `the walk took over 60 s`.
- `error`: the error text.

The warnings:


- `max_tabs` reached: audit `capped`, warning `keyboard: <path>: stopped after 150 Tab stops (keyboard.max_tabs); raise it if the page has more`
- A Tab press took the page away: audit `capped`, warning `keyboard: <path>: Tab stop <n> (<tag>) left the page; the rest of the page wasn't walked`
- 60 s per page: audit `timeout`, warning `keyboard: <path>: stopped after 60 s; the rest of the page wasn't walked`
- A widget key press took the page away: warning `keyboard: <path>: <key> on "<name>" left the page; skipped the rest of that widget`
- At most 2 reloads per page; after that the widget tests stop (trace event `widgets stopped: no reload left to reset the page`).
- A failure: audit `error`, warning `keyboard: <path>: <error>`; a trace that can't be saved: `keyboard: <path>: can't save the trace: <error>`.
- A capped or timed-out walk never reports a trap; its other issues are reported.

## Compare and confirm

- A keyboard issue from the first visit that the confirm visit's re-walk doesn't find is FIXED only when that re-walk finished clean (audit `ok`). When the re-walk was capped, timed out, failed or skipped it stays UNSTABLE and is never counted as fixed.
- Widgets are tested on each URL group's first page by path when the run's page list is known before the walk, so the same page is tested from run to run; otherwise on the first page of the group to be walked.
- A comparison tests each group's widgets on the page the snapshot tested them on (run.json `widget_pages`); its confirm visits test them on the page the comparison did. A widget or control issue missing from a page whose widgets weren't tested this time is not checked there (kept from the snapshot), never FIXED.

## Files

- `keyboard/<pageid>.json` in the run folder (mode 0600, at most 2 MB): the trace of the walk, schema `rhythm-soundcheck/keyboard-trace/v1`. It holds the page path (no query string; token-like segments masked), every forward and backward stop (selector, tag, role, masked name, box, whether it was hidden, covered or changed the page), the trap probe, the skip link test, the main landmark position, the widget and mouse-only tests, the focus ring measurements, the held requests and the events. Selectors inside open shadow roots and same-origin frames are joined with ` >>> `.
- `eaa/focus/<pageid>-<n>.png`: a crop of an element that failed `keyboard/no-focus-ring` (n is its Tab stop). Never written for a text field (text-like inputs, textareas, editable regions).
- run.json `keyboard` per page: `stops`, `wrapped`, `capped`, `skip_link`, `widgets`, `frames` (`<host>: <n> stops, trap yes|no` per cross-origin frame), `evidence` (the trace path), `crops` (issue key to crop path), `widget_kinds` (menu, dialog, details, disclosure), `ms` and `widgets_on` (the page's widgets and mouse-only controls were tested). run.json `widget_pages` lists those pages, one per URL group.
